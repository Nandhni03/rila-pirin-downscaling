# Log: Meridional Carpathians 2024 (same setup as the 2025 pilot, multicore products)

Goal (2026-10-21): downscale the whole year 2024 for the same Southern Carpathians rectangle as 2025
(see LOG.md), with every processing step that actually runs using multiple cores. Each entry: what was
done, why, and the result.

---

## 2026-10-21

### 1. Decisions (asked of the user)
- **Same DEM and mask as 2025** (`data/dem/meridionali_2025/`: 46 M px, 30 m, EPSG:3844), so the two years
  are directly comparable. The older `config_meridionali_2024.yml` (39 M px FABDEM_Meridionali2, for
  `run_year.py` and Nandhni's unreleased fork) was replaced; it is still in git (commit 4445e50).
- **Reuse the 2025 terrain instead of recomputing it.** The sky-view factor, slope/aspect, clustering
  (k = 2000) and horizon depend only on the DEM, the mask and the config, not on the year. Recomputing
  them would give identical numbers and cost ~4 h (2025: svf 2 h 31 min single core, clustering 65 min,
  horizon 19 min). Multicore effort therefore goes to the steps that do run for 2024.
- What does depend on the year and is recomputed: **solar geometry** (sun position for every hour),
  **ERA5**, **downscaling**, **daily statistics**, **GeoTIFFs and their checks**.

### 2. Config
- `config/config_meridionali_2024.yml` = the 2025 config with only the year, the name/description/date and
  the output directory (`data/meridionali_2024`) changed (checked with `diff`). DEM, mask, k, features,
  ERA5 settings and the output file names are identical.

### 3. Terrain caches copied (12:40)
- `ds_param.nc` (4.4 GB, terrain parameters and the cluster map), `df_centroids.pck` (the 2000 cluster
  centres) and `da_horizon.nc` (4.9 GB) copied from `data/meridionali_2025/outputs/` to
  `data/meridionali_2024/outputs/`; byte-identical (`cmp`, `md5sum`).
- Copies rather than links: the fork's `compute_dem_param` rewrites `ds_param.nc` when it loads it (LOG.md §27),
  and a link would let the 2024 run touch the 2025 file.
- `ds_solar.nc` is **not** copied: sun positions are per hour, so 2024 needs its own.
- Topoclass skips every terrain step whose cache exists, so the run goes straight to solar geometry.

### 4. ERA5 2024 downloaded (12:41-12:45)
- `scripts/fetch_era5_only.py` with the 2024 config → `data/logs/era5_2024_*.log`.
  EDH downloads up to 8 chunks at once (`edh_max_concurrency: 8`), so this step is already parallel.
- **228 s**, ~236 chunk requests. Same bbox and levels as 2025, so the same block folder and the same
  `ERA5.zarr` are used: the EDH fetcher rebuilds the store from all its blocks, so it now spans
  2023-12-11 .. 2026-01-28 (18720 h) and holds both years.
- Check: 2024 = **8784 h** (leap year), no NaN in t2m or t, t2m 252.4-315.3 K. Plausible.

### 5. Where the time went in 2025, and what is parallel for 2024
| step (2025) | time | cores in 2025 | 2024 |
|---|---|---|---|
| terrain parameters (svf) | 2 h 31 min | 1 | reused (§1) |
| clustering | 65 min | MiniBatchKMeans, partly multi-threaded | reused |
| horizon | 19 min | 8 processes | reused |
| solar geometry | 103 s | 20 (`CPU_cores`) | recomputed, already multicore |
| ERA5 | 6 min | 8 concurrent downloads | done, 228 s |
| downscaling | 4 min | 20 processes | already multicore |
| **monthly products** | **2 h 30 min** | **1** (one month after another) | **made parallel (§6)** |

The products were the only large step left on one core: per month, GeoTIFF export ~95 s per statistic and
the GeoTIFF checks ~180 s per statistic, all one after another.

### 6. Parallel products: what changed in the code
- Measured first on one 2025 file (January t_mean, written to a scratch folder): building the
  pixel → cluster map 31 s, peak 7.3 GB; export 94 s; checks 175 s, peak **10.3 GB**. Most of the check's
  memory went into recomputing, for every file, the map from 46 M pixel cluster names (strings) to clusters.
- `scripts/workflow.py`:
  - new `check_prep()`: the parts of the GeoTIFF checks that do not depend on the month (mask, the
    1000 random sample pixels, the grid, and the authors' pixel → cluster lookup) are computed **once**.
    The authors' lookup is still TopoPyScale's own expression (`.sel(point_name=<cluster map>)` as in
    `topo_plot.map_variable`), applied once to an index array instead of once per file to the values.
    It remains independent of the lookup used to write the GeoTIFFs (`pixel_index`).
  - `check_month()` takes these shared lookups (`prep=`). The checks themselves are unchanged: grid and
    CRS, nodata exactly outside the mask, every band against daily.zarr at the sample pixels, full band 1
    against the authors' expression, number of bands.
  - `rss_gb()` reports memory in the log.
- `scripts/run_year_public.py`, products in two phases:
  - **A, month by month** (seconds per month): hourly QA, `daily_stats`, write into daily.zarr. Kept in
    order because all months write into the same daily.zarr.
  - **B, in parallel**: one task per (month, statistic), so 12 × 3 = 36 tasks. Each does the GeoTIFF export and
    its checks. `--product-workers` (default 8) processes, started with `fork` after the pixel map and the
    check lookups exist, so all workers share them instead of each building its own (7-10 GB each).
  - Month markers (`months/YYYY-MM.json`) are written after phase B with the same content as before (QA,
    checks, timings per statistic). A month is `ok` only if its QA and all three statistics' checks pass.
  - The GeoTIFF format is unchanged (same as 2025), so the two years' files are directly comparable.

### 7. Test of the parallel products on 2025 data (12:55-13:10)
- Script `scratchpad/test_parallel.py` (temporary, outside the repo): took January and February 2025
  from the existing `daily.zarr`, ran the new phase B with 6 processes (6 tasks) into a scratch folder, then
  compared every band of every new GeoTIFF with the original 2025 GeoTIFF.
- Result: all 6 checks OK; **max |difference| = 0.0** and identical metadata (band dates, tags, grid,
  compression) for every file → the parallel path writes exactly the same files as the serial one.
- Speed: 6 tasks in **369 s** in parallel vs ~27 min one after another (≈ 4.4× faster with 6 processes).
  Each task gets slower when several run together (export 94 → ~170 s) because they share the disk and
  the compression threads, but the total is still much shorter.
- Memory: main process 4.3 GB after building the shared maps; the workers share it.

### 9. First attempt killed by the out-of-memory killer (13:20), restarted
- After 6 min 50 s, during `downscale_climate` (400/2000 points done), Linux killed the run:
  `Command terminated by signal 9`; `dmesg` shows `Out of memory: Killed process ... (python)`.
  The many `BrokenPipeError` messages that follow are only a consequence: the 20 downscaling workers
  lost the main process they report to.
- **Cause: my mistake.** The test from §7 was still running in the background (its last step, comparing
  every band with the 2025 files, is slow) and still held a few GB. The run (main process 11.7 GB + 20
  workers) plus the test did not fit in 23 GB RAM. In 2025 the same run fit because nothing else was running.
- Fix: stopped the test (`kill <pid>`), then ran the **same command again** →
  `data/logs/run_2024_<time>.log`. Nothing is lost: the downscaler records each finished cluster in
  `down.zarr.progress/` (440 files there) and skips them on restart; the terrain caches, solar geometry
  (`ds_solar.nc`, written before the crash) and ERA5 are reused.
- Test status: 2 of the 6 test files had been compared (identical, max |diff| 0.0); all 6 had passed
  the run's own checks. The comparison of the other 4 is repeated after the run, when the machine is free.
- Lesson: run one heavy job at a time on this machine (check with `htop` or `free -g` first).

### 11. Fix in `scripts/run_year_public.py` (13:59)
- **`--products-only`**: skips Topoclass entirely (terrain, ERA5 and downscaling are done) and runs only
  phase A + B from `down.zarr`. The main process then holds only the pixel map and the check lookups.
  In a full run (without the flag) the Topoclass object is now deleted before the products start.
- **Month marker written as soon as the month's 3 statistics are back** (`close_month()`), not at the end.
  A crash now loses only the months still in progress.
- **Per worker: GDAL cache 512 MB** (`rasterio.Env(GDAL_CACHEMAX=512)`) and **4 COG compression threads**
  instead of all 24.
- `finish()` no longer needs the Topoclass object.
- Restarted with 5 workers instead of 6 (14:00):
  ```
  ../venv/bin/python meridionali_zarr/scripts/run_year_public.py meridionali_zarr/config/config_meridionali_2024.yml \
      --products-only --product-workers 5 > meridionali_zarr/data/logs/products_2024_20261021_1400.log 2>&1
  ```
  Phase A runs again for all months (no marker yet; daily.zarr is simply rewritten with the same values).
  In phase B the 23 existing GeoTIFFs are not rewritten (`export_month` skips existing files), but they are
  checked again, so every month gets its marker with full check results.

### 12. Products run (14:00-14:39): **2024 complete, all checks passed**
Log: `data/logs/products_2024_20261021_1400.log`. `YEAR COMPLETE, ALL CHECKS PASSED`, exit 0.
- Wall time **39 min** (phase A 4.5 min, pixel map 34 s, check lookups 7 s, GeoTIFFs 33.5 min on 5 processes).
  Peak RSS of the main process 8.4 GB.
- **Memory stayed comfortable:** 9-11 GB RAM used, ≥ 12.8 GB available, swap ≤ 5 GB (vs RAM full and swap
  30 GB before the fix). The swap use is Linux moving the idle main process's pages to disk.
- All 12 months `ok` in `outputs/months/2024-MM.json` (QA, the checks of the 3 GeoTIFFs, timings), summary in

- Per task: re-checking an existing file 165-195 s; writing + checking a new one ~180-200 s + ~190-210 s.
  Every GeoTIFF: grid = DEM, nodata exactly outside the mask, all bands = daily.zarr at 1000 sample pixels

- `geotiff/t_{mean,min,max}_daily_2024-MM.tif`: 36 files, 30 m, EPSG:3844, one band per day, **87 GB**

**Time, 2024 vs 2025:**
